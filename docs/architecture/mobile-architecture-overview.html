01 · Executive Summary

What we're building, and the four rules that shape it

Flipper.ai today is a Next.js 16 web app on Cloud Run that scrapes five marketplaces, scores flip opportunities with AI, and tracks every flip from discovery to profit. The mobile track ships that same product as a native iOS + Android app — not a companion, a peer — so users can scan, negotiate, and close deals from a parking lot.

Guiding principles

1. Pipeline before product Epic 16 (CI/CD) lands before any feature epic. From Phase A onward, every merged story is on testers' phones within minutes — no "big bang" integration at the end.
2. One backend, zero forks Mobile is a new client of the existing Cloud Run API. Backend changes are strictly additive: Bearer-token auth, a DeviceToken model, a RevenueCat webhook, a min-version endpoint, a push channel in the dispatcher.
3. One identity, one design language Same Firebase project (same User.firebaseUid), same Prisma tier source-of-truth, and the same fp-* dark-glassmorphism tokens — extracted to packages/design-tokens/ and rendered natively via NativeWind.
4. Real AI, never mocked Project-wide policy: tests exercise the real Groq → Gemini → OpenAI fallback chain through the backend /api/* endpoints. No stubs, no escape hatches — on mobile exactly as on web.

The four release phases

Phase A Rails up — Epics 15–17 (17 stories, ≈2 wk). Monorepo, EAS pipeline, auth bridge. A stub-but-real binary lands on TestFlight + Firebase App Distribution.
Phase B Lovable beta — Epics 18–21 (25 stories, ≈6 wk). Shell, scanning, lifecycle Kanban, push. First product-grade closed beta.
Phase C Feature parity — Epics 22–27 (28 stories, ≈10 wk). Messaging, reposting, analytics, IAP, settings + a11y, meetups. Open beta, parity with web.
Phase D Launch — Epics 28–29 (10 stories, ≈3 wk). Camera, offline, tablet, store GA. v2.0.0 on both stores.
Where we are today (2026-06-12): Epic 15 is in progress — all five foundation stories are ready-for-dev. Epics 16–29 are fully planned and sit in the backlog.

The stack optimizes for one thing: a single TypeScript-fluent team shipping two native platforms from one codebase, with maximum reuse of what the web app already proved.

07 · Key Runtime Flows

Four flows that define the architecture

These sequences are where mobile genuinely differs from web — everything else is the same API contract with a native skin.

🔐 Auth bridge — Firebase ID token → Bearer (Epic 17)
Sign in with email/password, Google, or Apple via the Firebase SDK — same Firebase project as web, so the UID is identical on both platforms.
SDK returns an ID token; it is written to expo-secure-store (iOS Keychain / Android Keystore) — never AsyncStorage (NFR-MOB-SEC-01).
Every API call sends Authorization: Bearer <token>. onIdTokenChanged() refreshes silently and rewrites secure storage.
Backend getCurrentUserId() now checks cookie OR Bearer: Bearer path verifies via Admin SDK verifyIdToken() → looks up User.firebaseUid → returns the Prisma user id. Web is untouched.
Optional biometric unlock (Face ID / fingerprint) gates the cached session — it never replaces the Firebase credential.
📡 Scan with live progress — SSE first, polling fallback (Epic 19)
User taps a marketplace (or a saved-search chip) → POST /api/scraper/start — the very same endpoint the web Scanner uses.
App subscribes to SSE /api/events for job progress (listings-found counts, completion). On flaky cellular, it falls back to short-interval polling of /api/scraper/jobs/:id.
Results stream into the listings feed; scores ≥85 get the hot-card glow; ≥70 become opportunity candidates (same thresholds as web).
Feed pages are written to the MMKV-persisted TanStack Query cache — next cold launch renders instantly before any network call.
One tap saves a listing as an Opportunity (POST /api/opportunities) with a success haptic; pass marks passedAt so it never resurfaces.
🔔 Push notification — event → pocket (Epic 21)
On login, the app registers its Expo push token: POST /api/users/me/devices → DeviceToken row (platform, token, app version, lastSeenAt).
A user-facing event fires server-side (new hot opportunity, inbound message, flip sold, price drop — the full FR-NOTIFY-01..11 set).
The existing dispatcher (email Epic 10, web FCM Epic 11) routes through the new MobilePushChannel — honoring per-event × per-channel preferences and server-enforced quiet hours.
Expo Push API fans out to APNs (iOS) + FCM (Android). Payload carries title, body, deep-link route, and an iOS action category.
Background: OS tray + badge counts; action buttons ("Mark Sold", "Approve & Send") hit the backend via background fetch. Foreground: in-app toast with tap-to-navigate; SSE keeps screens live without push.
💳 IAP entitlement sync — RevenueCat ↔ Stripe (Epic 25)
Mobile reads the user's tier from /api/users/me — Prisma is the single source of truth, fed by Stripe (web) and RevenueCat (mobile).
FREE users see IAP offers: FLIPPER / PRO, monthly + annual (flipper_monthly_v1… SKUs identical in both stores). Purchase runs through StoreKit 2 / Play Billing via react-native-purchases.
RevenueCat validates the receipt and fires its webhook → POST /api/webhooks/revenuecat → updates User.subscriptionTier, mirroring the Stripe webhook handler.
Double-billing guard: users with an active web Stripe subscription are never offered IAP unless they explicitly migrate. Feature gates render client-side as UX but are enforced server-side as authority.
"Restore Purchases" (App Store requirement) and OS-level manage/cancel deep links live in Settings → Subscription.

10 · Design Decisions

Architecture Decision Records — the "why" behind each call

Twelve decisions shape this plan. Each one lists the choice, the reasoning, and what was rejected.

ADR-01 Expo managed workflow + EAS, not bare React Native or native Swift/Kotlin

Decision
Build with Expo SDK 53+ managed workflow; EAS handles builds, signing, submission, and OTA updates.

Reasoning
One TypeScript codebase covers both platforms with the team's existing React skills. Managed workflow eliminates Xcode/Gradle project maintenance, EAS owns code-signing credentials, and every native need in the plan (camera, calendar, geofencing, notifications, secure storage, share extension) is covered by maintained Expo modules.

Rejected
Native Swift + Kotlin: two codebases, no shared types. Flutter: abandons the TypeScript type-sharing with packages/types/. Bare RN: all the native maintenance with none of the EAS leverage.

ADR-02 Monorepo with pnpm workspaces, not a separate mobile repo

Decision
Add mobile/ and packages/ workspaces beside the existing Next.js root (Story 15.1).

Reasoning
Domain types and design tokens are shared by import, not by copy — a change to Opportunity breaks both compiles immediately rather than drifting silently. One PR can update API + mobile consumer atomically; one CI config; one set of conventions (lint, headers, changelog).

Rejected
Separate repo: guarantees type drift, doubles release ceremony, splits the acceptance-test tree that must stay unified (test/acceptance/).

ADR-03 Reuse the existing backend wholesale — additive changes only

Decision
Mobile is a pure client of the existing Cloud Run API. Five additive changes total (Bearer auth, DeviceToken, push channel, RevenueCat webhook, min-version endpoint). No BFF, no GraphQL gateway, no mobile-specific API tier.

Reasoning
The API already serves a responsive web client with the same shapes mobile needs; the RFC 7807 error envelope and retryable flags translate directly. A BFF would add a deployment, a contract, and a failure mode while saving nothing.

Rejected
GraphQL/BFF layer: real cost, speculative benefit at this product size.

ADR-04 Bearer-token session bridge rather than cookie sessions on mobile

Decision
getCurrentUserId() accepts Authorization: Bearer <Firebase ID token> (verified via Admin SDK) alongside the existing __session cookie (Story 17.1).

Reasoning
Native HTTP stacks don't share the browser cookie jar, and the 5-day session cookie model fits browsers, not apps. Firebase ID tokens refresh silently via the SDK, live in hardware-backed secure storage, and carry the same UID — so the user row resolution (firebaseUid → Prisma id) is unchanged.

Rejected
Replicating cookie session issuance on mobile (fragile webview dance); a parallel API-key scheme (second identity system to audit).

ADR-05 NativeWind v4 consuming shared design tokens, not StyleSheet or styled-components

Decision
Extract color/spacing/radius/typography/glass-alpha tokens to packages/design-tokens/; expose the canonical fp-* utility set (glass, glow-card, hot-card, btn, badge, grad, alert) as NativeWind classes.

Reasoning
The dark-glassmorphism language (purple #7c3aed on #080b14) is the brand. One token source means web and mobile can't diverge, and web engineers already think in these utility names.

Rejected
StyleSheet objects (token duplication, no utility ergonomics); styled-components (runtime cost, different idiom from web Tailwind).

ADR-06 Pipeline-first sequencing — Epic 16 lands before any feature epic

Decision
Phase A ships monorepo (15) → CI/CD (16) → auth (17) before the first screen of product UI exists.

Reasoning
Mobile release friction (signing, review queues, store policy) is the schedule risk — so it's retired first, while the surface area is a stub. From Epic 18 onward, every merged story reaches testers' phones within minutes, making beta feedback continuous instead of milestone-gated.

Rejected
Features-first with a "release hardening" phase at the end — the classic way mobile launches slip by quarters.

ADR-07 SSE in foreground + push in background, with polling fallback

Decision
Foreground real-time reuses the web's SSE /api/events stream; background events arrive as Expo push (APNs/FCM); flaky-cellular degrades SSE to short-interval polling.

Reasoning
SSE already exists and is proven on web — no new server infra. Push is the only reliable background channel on mobile OSes. WebSockets would add a second bidirectional protocol for no additional capability the product needs.

Rejected
WebSockets (new infra, same outcome); push-only (foreground latency and permission dependence); polling-only (battery + staleness).

ADR-08 RevenueCat for IAP, with Prisma tier as the single source of truth

Decision
Subscriptions purchased on mobile go through RevenueCat (react-native-purchases) over StoreKit 2 / Play Billing; its webhook updates User.subscriptionTier exactly as Stripe's does. Web-Stripe subscribers are never offered IAP (double-billing guard).

Reasoning
Store policy mandates IAP for mobile-originated digital subscriptions — Stripe Checkout in a webview is a rejection. RevenueCat removes receipt-validation servers from scope and gives one dashboard across both stores. Keeping entitlement authority in Prisma means feature gates read one field regardless of payment rail.

Rejected
Direct StoreKit/Billing integration (receipt validation + cross-store reconciliation becomes our code); webview Stripe (policy violation).

ADR-09 TanStack Query + MMKV for state; offline as Phase D polish, not a Phase A constraint

Decision
All server state lives in TanStack Query with an MMKV persister from Epic 19; the offline write-through queue and full optimistic-UI pattern land in Epic 28.

Reasoning
Persisted queries give 90% of the perceived-offline value (instant launch, readable history) for 10% of the complexity. Full write-queue semantics (ordering, conflict rollback) are genuinely hard — scheduling them after the data model has stabilized in beta avoids building sync logic on moving sand.

Rejected
Redux + custom persistence (boilerplate without cache semantics); offline-first from day one (highest-risk work at the point of least knowledge).

ADR-10 Maestro for mobile E2E, keeping Gherkin acceptance in the shared tree

Decision
UI-visible ACs are verified by Maestro YAML flows on iOS Simulator + Android Emulator in CI; Gherkin feature files E-015…E-029 live in the same test/acceptance/features/ tree and traceability matrix as web.

Reasoning
Maestro's declarative flows are fast to write, stable in CI, and run both platforms — the ≤8-minute smoke budget is realistic. One acceptance tree preserves the FR → story → scenario traceability discipline already enforced on web.

Rejected
Detox (heavier setup, flake-prone on CI emulators); Appium (slow, verbose); splitting mobile acceptance into a second matrix (kills single-source traceability).

ADR-11 Real AI calls in every test layer — the never-mock policy extends to mobile

Decision
Mobile tests that touch AI features exercise the real backend /api/* endpoints, which route through the live Groq → Gemini → OpenAI chain (Anthropic for Tier-2 analysis). No stubs, no fixtures, no interception.

Reasoning
AI behaviour is the product for message generation, scoring, and listing copy — a mocked response validates nothing. Rate-limit pressure is handled at the root: Groq-primary routing, retry/backoff tuning, @serial sequencing, response caching in AiAnalysisCache.

Rejected
Any mock/stub/escape-hatch pattern — explicitly forbidden in CLAUDE.md, and the mobile DoD restates it per story.

ADR-12 Phased store rollout with OTA rollback and server-side force-upgrade

Decision
Production releases roll out 10% → 25% → 50% → 100% on both stores, with Sentry crash-free-rate gates between steps; make mobile-rollback republishes the prior OTA update; /api/mobile/min-version can force-upgrade stragglers.

Reasoning
Mobile mistakes are sticky — a bad binary lives on devices until users update. Phasing caps the blast radius, OTA rollback fixes JS-level regressions in minutes, and the min-version gate ends support for broken versions deterministically.

Rejected
100% releases with hotfix-by-review (review latency makes incidents day-scale instead of minute-scale).

13 · Testing & Quality

The quality gate every story passes — no exceptions

The mobile DoD mirrors the web DoD: traceable acceptance tests at the right level, both platforms, real AI, and zero regression on the existing web suites.

Test pyramid

LevelToolingScope & gates
UnitJest (mobile/src/__tests__/)All new business logic; ≥80% statements / 70% branches on new modules
E2EMaestro flowsEvery UI-visible AC, on iOS Simulator AND Android Emulator; smoke pack ≤8 min in CI
AcceptanceCucumber/GherkinOne feature file per epic: E-015-mobile-foundation.feature … E-029-mobile-launch.feature, in the shared test/acceptance/features/ tree
StaticESLint flat config · tsc strict · expo doctor · pnpm auditZero errors, zero warnings from expo doctor, no critical CVEs
Regressionmake test + make test-acceptanceFull web suites stay green on every mobile PR
Triple tagging, enforced: every Gherkin scenario carries @E-NNN-S-YYY (epic-scoped scenario id) + @story-X-Y + @FR-…/@NFR-MOB-… — feeding the single requirements-traceability matrix shared with web. A missing tag is a DoD failure.

Per-story DoD highlights

✅ Every AC verified on both iOS Simulator and Android Emulator
✅ Test level matches the AC — UI-visible ACs get Maestro/E2E, logic ACs get Jest; a mocked service call never satisfies a UI AC
✅ EAS preview build succeeds for both platforms before review
✅ Sentry source maps verified uploaded for the test build
✅ VoiceOver / TalkBack navigation order logical; touch targets ≥44pt/48dp; contrast ≥ WCAG AA
✅ AI-touching stories exercise the real Groq → Gemini → OpenAI chain — never mocked
✅ File headers on every new .ts/.tsx; CHANGELOG entry for user-visible changes
✅ Traceability matrix updated; Trello card moved on the trello-axovia board

Why this much rigor on a mobile app?

Web mistakes deploy forward in minutes; mobile mistakes live in pockets until users choose to update. The DoD front-loads the cost of correctness because the rollback story (OTA ≤5 min, phased rollout, force-upgrade) only covers JS — a broken native binary is a week-long incident. Cheap insurance, bought per-story.
